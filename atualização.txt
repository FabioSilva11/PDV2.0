OBJETIVO GERAL
Quero evoluir o PDV2.0 para operar com UMA ÚNICA BASE DE CÓDIGO e com dois clientes de operação:

1. SITE/WEB
2. APLICATIVO ANDROID

Os dois usam o mesmo backend Express, o mesmo SQLite, o mesmo modelo de pedido e as mesmas regras de impressão.

A principal simplificação da arquitetura é:

- o SITE é responsável por definir o ambiente operacional;
- o ambiente é obrigatoriamente RESTAURANTE ou LANCHE;
- o SITE gera uma configuração de terminal, preferencialmente por QR Code;
- o APP ANDROID apenas recebe essa configuração e a salva;
- o Android NÃO deve pedir para o operador escolher RESTAURANTE/LANCHE manualmente;
- o Android NÃO deve criar uma lógica de pedido diferente da WEB;
- pedidos feitos pelo SITE funcionam mesmo sem nenhum APP ANDROID instalado.

O servidor continua tendo um IP/hostname e uma porta. O ambiente NÃO cria um IP diferente. O SITE apenas associa o servidor à configuração do ambiente e gera os dados que o Android precisa para se conectar.

Exemplo:

Servidor do PDV:
  http://192.168.1.100:3001

Site configurado como:
  RESTAURANTE

Terminal Android configurado pelo QR Code:
  servidor = http://192.168.1.100:3001
  ambiente = restaurante

Outro terminal pode usar o mesmo servidor:
  servidor = http://192.168.1.100:3001
  ambiente = lanche

Não hardcode um IP real do estabelecimento no código. O endereço deve ser configurável.

IMPORTANTE:
Não quero criar um segundo sistema de PDV separado para Android. O Android deve reutilizar a aplicação React/TypeScript existente, com a camada nativa mínima necessária para gerar um APK instalável.

2. REGRA DE NEGÓCIO CENTRAL
============================================================

Existem CINCO impressoras físicas:

1. Espelho do Lanche
2. Cozinha do Lanche
3. Sucos
4. Espelho Restaurante
5. Cozinha Restaurante

O PEDIDO é um único pedido comercial.
Mesmo que sejam misturados itens Restaurante, Lanche e compartilhados, continua existindo apenas UM pedido, com UM número, UMA conta e UM histórico.

A origem do atendimento é determinada pela configuração do cliente que criou o pedido:

SITE/WEB:
- site configurado como RESTAURANTE -> pedido nasce em RESTAURANTE;
- site configurado como LANCHE -> pedido nasce em LANCHE.

ANDROID:
- terminal configurado pelo SITE como RESTAURANTE -> pedido nasce em RESTAURANTE;
- terminal configurado pelo SITE como LANCHE -> pedido nasce em LANCHE.

Essa origem deve ser gravada no pedido no momento da criação e permanecer imutável depois.

IMPORTANTE:
- o SITE pode criar pedidos sem o APP ANDROID;
- o APP ANDROID não escolhe o ambiente manualmente;
- o ambiente do Android vem da configuração recebida do SITE;
- SITE e Android usam o mesmo Order, backend, SQLite, regras de negócio e roteamento de impressão;
- a origem do pedido NÃO deve ser inferida olhando os produtos.

Exemplo:

Site = RESTAURANTE
ou
Terminal Android = RESTAURANTE

pedido:
  origemAtendimento = restaurante

Site = LANCHE
ou
Terminal Android = LANCHE

pedido:
  origemAtendimento = lanche

A origem do pedido é definida antes da criação e fica salva no próprio Order.

============================================================
3. DIFERENÇA ENTRE AMBIENTE, CATÁLOGO E ITEM
============================================================

Não misture estes conceitos.

A) AMBIENTE DO SITE
É o ambiente operacional configurado no site/instância:

- restaurante
- lanche

Esse campo é obrigatório na configuração inicial do site.

B) CONFIGURAÇÃO DO TERMINAL ANDROID
É a configuração recebida do SITE para aquele aparelho:

- deviceId
- ambienteOperacional
- serverBaseUrl
- configuradoEm

O operador do Android não escolhe o ambiente manualmente. O terminal apenas recebe, salva e utiliza a configuração do SITE.

C) ORIGEM DO ATENDIMENTO
É copiada do ambiente configurado no cliente que criou o pedido:

- Site Restaurante -> restaurante
- Site Lanche -> lanche
- Android configurado como Restaurante -> restaurante
- Android configurado como Lanche -> lanche

D) CATÁLOGO DO ITEM
É o cardápio de onde o item foi selecionado:

- restaurante
- lanche

Um pedido pode ter itens de qualquer catálogo e continuar sendo um único pedido.

O catálogo do item NÃO muda a origem do atendimento.

Exemplo:

Terminal = RESTAURANTE

Pedido:
- Carne de Sol
- X-Salada
- Pizza
- Suco

Continua:
  origemAtendimento = restaurante

O catálogo pode continuar sendo alterado livremente para permitir pedidos mistos.

4. NOVOS TIPOS DE DADOS
============================================================

No src/types.ts crie tipos explícitos e reutilizáveis.

Sugestão:

export type OperatingEnvironment = 'restaurante' | 'lanche';

Adicione uma configuração equivalente para o SITE/WEB:

interface SiteSettings {
  siteId: string;
  ambienteOperacional: OperatingEnvironment;
  configuradoEm: string;
  atualizadoEm: string;
}

Adicione ao terminal/dispositivo uma configuração equivalente a:

interface DeviceSettings {
  deviceId: string;
  ambienteOperacional: OperatingEnvironment;
  serverBaseUrl: string;
  configuradoEm: string;
  atualizadoEm: string;
}

Atenção: no Android, ambienteOperacional é recebido da configuração gerada pelo SITE. Não criar um seletor livre de ambiente para o operador.

O nome exato pode ser adaptado à arquitetura existente, mas a informação deve ser persistida.

No Order adicione:

origemAtendimento?: OperatingEnvironment;

Prefira tornar esse campo obrigatório nos novos pedidos, mas mantenha compatibilidade de migração para pedidos antigos.

Também é recomendado adicionar ao CartItem:

catalogoOrigem?: MenuCatalog;

Esse campo registra de qual catálogo o atendente selecionou o item.

IMPORTANTE:
catalogoOrigem do item é histórico/proveniência.
Ele NÃO deve ser usado para decidir para qual cozinha completa o pedido será enviado.

============================================================
ADENDO A — PEDIDOS PELO SITE/WEB, SEM APP ANDROID
============================================================

O PDV2.0 também deve permitir criar pedidos diretamente pela versão WEB,
sem exigir o aplicativo Android.

O site é um cliente do mesmo sistema. Ele NÃO é um segundo PDV e NÃO deve
criar backend, banco, modelo Order ou lógica de impressão separados.

A versão WEB deve utilizar:
- o mesmo Order;
- as mesmas regras de negócio;
- o mesmo backend Express;
- o mesmo SQLite;
- as mesmas regras de impressão;
- o mesmo número comercial por pedido;
- a mesma função central de roteamento de impressão.

A.1 CONFIGURAÇÃO INICIAL OBRIGATÓRIA DO SITE

Na configuração inicial do site, além das informações atuais do estabelecimento,
deve existir uma opção OBRIGATÓRIA para selecionar o ambiente:

[ RESTAURANTE ]
Pedidos e operação do ambiente Restaurante

[ LANCHE ]
Pedidos e operação do ambiente Lanche

Não permitir finalizar a configuração do site sem escolher um ambiente.

A escolha deve ser persistida como configuração daquele site/instância.
Não assumir o ambiente pelo catálogo de produtos.

A.2 REGRA DE ORIGEM DOS PEDIDOS DO SITE

Site configurado como RESTAURANTE:
- todo pedido criado pelo site recebe:
  origemAtendimento = restaurante

Site configurado como LANCHE:
- todo pedido criado pelo site recebe:
  origemAtendimento = lanche

A atribuição deve acontecer no momento da criação do pedido e ser preservada
no próprio Order.

A interface de venda do site NÃO deve permitir ao operador escolher manualmente
a origem do pedido. A origem vem da configuração do site.

A.3 PEDIDOS DO SITE PODEM SER MISTOS

O site deve continuar permitindo produtos do catálogo Restaurante, do catálogo
Lanche e itens compartilhados.

Exemplo:

Site = RESTAURANTE

Pedido 700:
- Carne de Sol
- X-Salada
- Pizza
- Suco

Resultado:

origemAtendimento = restaurante

Continua sendo UM único pedido comercial.

A.4 IMPRESSÃO DOS PEDIDOS CRIADOS PELO SITE

Os pedidos criados pelo site devem passar pela mesma função:

resolveOrderPrintDestinations(order)

Não criar uma segunda lógica de impressão apenas para WEB.

Site Restaurante:
- Cozinha Restaurante -> pedido completo
- Espelho Restaurante -> pedido completo
- Sucos -> somente sucos
- Cozinha Lanche -> nada
- Espelho Lanche -> nada

Site Lanche:
- Cozinha Lanche -> pedido completo
- Espelho Lanche -> pedido completo
- Sucos -> somente sucos
- Cozinha Restaurante -> nada
- Espelho Restaurante -> nada

A mesma regra vale para pedidos criados pelo Android.

A.5 ORIGEM DO CLIENTE X ORIGEM DO ATENDIMENTO

Manter esses conceitos separados.

Pode existir:

origemCliente = 'web' | 'android'

e:

origemAtendimento = 'restaurante' | 'lanche'

Isso permite identificar:
- qual cliente criou o pedido;
- em qual ambiente o atendimento nasceu.

Não usar origemCliente como substituto de origemAtendimento.

A.6 CONFIGURAÇÃO E ALTERAÇÃO DO AMBIENTE DO SITE

A configuração deve ser recuperável após reinicialização do site.

Criar área administrativa para:
- visualizar ambiente atual;
- visualizar configuração do estabelecimento;
- alterar ambiente;
- confirmar alteração;
- registrar auditoria.

Não permitir troca silenciosa enquanto houver carrinho/pedido em andamento.

A alteração não pode mudar retroativamente pedidos já criados.

A.7 FONTE DE VERDADE

Para pedidos WEB:
- a origem vem da configuração do site no momento da criação.

Para pedidos ANDROID:
- a origem vem da configuração do terminal no momento da criação.

Para ambos:
- o Order salvo é a fonte histórica;
- catalogoOrigem é somente proveniência do item;
- o catálogo nunca redefine origemAtendimento;
- reimpressão utiliza o histórico do job/order, não uma nova inferência.

RESTAURANTE

11. IP FIXO
============================================================

Não confundir:
"IP fixo" não significa IP escrito permanentemente no código.

O estabelecimento terá um computador/servidor com IP reservado/estático na LAN.

O aplicativo deve guardar esse endereço.

Exemplo de configuração real:
http://192.168.0.50:3001

Mas esse valor deve vir da tela de configuração.

Criar validação de:
IPv4 válido
porta 1..65535

Aceitar também hostname somente se for útil à arquitetura, mas tratar IP como caso principal.

Não permitir URL arbitrária sem validação básica.

Não aceitar esquemas perigosos como:
javascript:
file:
content:

O objetivo é permitir:
http://192.168.x.x:3001
https://servidor.exemplo

A. Espelho do Lanche
B. Cozinha do Lanche
C. Sucos
D. Espelho Restaurante
E. Cozinha Restaurante

REGRA:

A impressora de COZINHA do ambiente de origem recebe o PEDIDO COMPLETO.

19. REGRA DA IMPRESSORA SUCOS
============================================================

A impressora "Sucos" é compartilhada pelos dois ambientes.

Ela NÃO deve depender da origem do atendimento.

Ela deve imprimir somente itens que pertencem à categoria de sucos.

Preferir identificação estável:

categoriaId = 'cat-sucos'

ou equivalente já existente no sistema.

Não usar somente:

estacaoProducao === 'bar'

porque existem outras bebidas e produtos que podem utilizar a estação bar.

Assim:

if item is suco:
    Sucos recebe
else:
    Sucos não recebe

Isso vale para:
- pedido inicial;
- espelho;
- reimpressão controlada.

============================================================

Espelho do Lanche recebe o pedido COMPLETO.

A impressora de espelho do outro ambiente não recebe nada.

A impressora Sucos recebe apenas os itens de suco correspondentes ao espelho.

23. ATENÇÃO A PRODUTOS MULTICATÁLOGO
============================================================

Existem produtos que podem aparecer nos dois catálogos.

Isso NÃO pode provocar duplicação entre cozinhas.

Exemplo:

Batata/Porção que aparece em Restaurante e Lanche.

Se foi adicionada ao pedido:

origemAtendimento = restaurante

então:
- Cozinha Restaurante recebe o pedido completo;
- Cozinha Lanche não recebe nada;
- eventual impressora específica só deve receber a saída explicitamente configurada para esse tipo de item.

Na nova regra da via principal, nunca usar:
normalizeCatalogos(menuItem)
como critério para decidir qual cozinha principal imprime.

O catálogo pode continuar sendo usado:
- para filtrar o cardápio na interface;
- para saber onde o produto é vendido;
- para relatórios;
- para origem do item;
- para regras específicas.

Mas não para escolher a cozinha principal do pedido.

36. MULTI-CLIENTE — PONTO CRÍTICO
============================================================

ATENÇÃO:

O projeto atual possui LocalStore + snapshots completos no frontend e POST/GET de snapshot no backend.

Com Android + navegador + mais de um terminal escrevendo ao mesmo SQLite, NÃO é seguro simplesmente deixar dois clientes sobrescreverem o snapshot inteiro.

Isso pode causar:
- perda de pedidos;
- perda de pagamentos;
- conflito de conta;
- perda de impressões;
- último escritor vencendo.

Portanto, antes de declarar a arquitetura multi-terminal pronta, implementar proteção de concorrência.

Preferência:

A) API transacional do backend para operações críticas.

Ou, no mínimo:

B) versionamento do snapshot:
- servidor mantém revision;
- cliente informa baseRevision;
- servidor rejeita gravação obsoleta com 409;
- cliente recarrega e reconcilia;
- nunca sobrescreve silenciosamente dados mais novos.

Para operações críticas, prefira endpoints específicos no backend:
- criação de pedido;
- adição de itens;
- pagamento;
- espelho;
- alteração de estado;
- impressão;
- configuração.

Não é necessário reescrever todo o sistema imediatamente, mas não deixe o Android depender de um "último snapshot ganha" sem proteção.

Documentar qualquer parte ainda baseada em snapshot.

37. API DE CONFIGURAÇÃO DO TERMINAL
============================================================

A configuração do terminal deve ser gerada pelo SITE.

O SITE deve possuir uma área para gerar uma configuração de terminal:

- ambiente: RESTAURANTE ou LANCHE;
- serverBaseUrl;
- token/código de pareamento opcional;
- QR Code.

Pode existir uma API como:

GET /api/terminal/config
POST /api/terminal/pair

ou outra equivalente, desde que o fluxo permaneça simples.

O principal objetivo é que o Android receba a configuração em vez de escolher o ambiente.

A configuração continua pertencendo ao dispositivo/terminal, mas sua fonte de criação é o SITE.

O servidor pode registrar:
- deviceId;
- ambiente atual;
- última conexão;
- data da configuração.

Não salvar "ambiente = restaurante" como configuração global única para todo o restaurante, porque podem existir vários terminais em ambientes diferentes.
