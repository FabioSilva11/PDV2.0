1. OBJETIVO PRINCIPAL
   ==================================================

Quero atualizar a arquitetura atual do PDV 2.0 para separar claramente:

1. SITE/PDV COMPLETO
2. APLICATIVO ANDROID PARA GARÇONS E ATENDENTES
3. SERVIDOR/API CENTRAL
4. BANCO DE DADOS CENTRAL
5. SISTEMA CENTRALIZADO DE IMPRESSÃO

O aplicativo Android NÃO deve ser uma representação completa do site.

O aplicativo Android será um cliente operacional especializado exclusivamente para garçons e atendentes.

O SITE continuará sendo o sistema completo de PDV, administração e operação.

A arquitetura final deve ser:

```
                REDE LOCAL

            ┌──────────────────────┐
            │    SERVIDOR PDV      │
            │                      │
            │ Node.js / Express    │
            │ REST API             │
            │ SQLite               │

            │ Pedidos              │
            │ Mesas                │
            │ Contas               │
            │ Pagamentos           │

         ┌─────────────┴─────────────┐
         │                           │
   ┌─────▼──────┐              ┌─────▼──────┐
   │ SITE / PDV │              │ APP ANDROID│
   │ COMPLETO   │              │ GARÇONS    │
   │ WEB        │              │ ATENDENTES │
   └────────────┘              └────────────┘
```

Os dois clientes devem utilizar a mesma API e o mesmo banco central.

O Android NÃO deve manipular diretamente o SQLite.

O Android NÃO deve conter a lógica principal de impressão.

O Android NÃO deve depender do React do site para funcionar.

O Android deve possuir interface própria e fluxo próprio.

========================================

Hoje o projeto utiliza grande parte da lógica de negócio dentro do frontend React, especialmente no RestaurantContext, e a persistência ocorre através de snapshot do banco.

Esse modelo deve ser alterado.

A nova arquitetura deve transformar o servidor em fonte oficial da verdade.

↓
SERVIDOR
↓
BANCO DE DADOS

ANDROID
↓
REST API
↓
SERVIDOR
↓
BANCO DE DADOS

Não fazer:

ANDROID
↓
código do SITE
↓
estado local do React
↓
snapshot completo

8. PEDIDO MISTO
===============

Preservar esta regra fundamental.

Um pedido pode conter simultaneamente produtos associados ao restaurante e ao lanche.

Esse pedido NÃO deve ser dividido em dois pedidos comerciais.

Ele continua sendo um único pedido.

Exemplo:

Pedido 125

1x Prato restaurante
1x Hambúrguer lanche
1x Batata lanche
1x Suco
1x Refrigerante

O pedido continua sendo:

Pedido 125

O sistema pode gerar diferentes jobs de impressão conforme as regras.

A via principal da cozinha deve continuar podendo apresentar o pedido completo quando essa for a regra do ambiente de atendimento.

10. IMPORTANTE: IMPRESSÃO NO SERVIDOR
=====================================

O Android não deve conhecer diretamente:

* IP das impressoras;
* USB das impressoras;
* protocolo ESC/POS;
* fila física;
* retry;
* reconexão;
* fallback;
* configuração de impressora.

Essas responsabilidades devem permanecer no servidor.

Fluxo:

Android
→ POST /api/orders
→ servidor salva pedido
→ servidor calcula jobs
→ servidor coloca jobs na fila
→ PrinterManager processa
→ impressora física imprime

O Android recebe apenas o resultado da operação.

Exemplo de resposta:

{
"success": true,
"order": {...},
"printing": {
"queued": true,
"jobs": [...]
}
}

Não bloquear a criação do pedido somente porque uma impressora temporariamente está indisponível.

O pedido deve ser persistido e o job de impressão deve possuir estado próprio.

Não imprimir duplicadamente apenas porque o cliente repetiu a requisição.

12. IDEMPOTÊNCIA
================

Essa parte é obrigatória.

O Android pode perder conexão depois que o servidor criou o pedido.

Quando o aplicativo tentar novamente, o sistema não pode criar dois pedidos.

Para operações críticas, utilizar:

* requestId
* operationId
* clientTransactionId
* ou outro mecanismo equivalente.

Exemplo:

POST /api/orders

Header:

Idempotency-Key: UUID

O servidor deve detectar uma requisição repetida e devolver o resultado original quando apropriado.
